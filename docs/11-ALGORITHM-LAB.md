# 11. 알고리즘 실험실 (누적 문서)

`01-ALGORITHM.md` 는 **현행 확정 스펙**이다. 이 문서는 **왜 그렇게 되었고,
무엇을 시도해 무엇을 기각했는지**를 남긴다. 곡선 하나를 바꾸려는 사람이
같은 함정을 다시 밟지 않게 하는 것이 목적이다.

## 기재 규칙

- 변경은 **가설 → 검증 방법 → 결과 → 채택/기각** 순으로 적는다
- 기각한 것도 남긴다. 다시 제안될 때 근거가 된다
- 채택하면 `ALGORITHM_VERSION` 을 올리고 여기에 버전을 적는다
- 골든 케이스 점수가 바뀌면 이전 값과 새 값을 함께 적는다

---

## 현재 상태

| 항목 | 값 |
|---|---|
| 알고리즘 버전 | `v1.0.1` |
| 가산축 | 10개 (합 100) |
| 감점축 | RISK (최대 −15) |
| 단위 테스트 | 118건 |
| 골든 케이스 | 3종 (우수 / 중간 / 열위) |

골든 케이스는 절대 점수가 아니라 **순서**를 고정한다. 우수 > 중간 > 열위가
깨지면 실패한다. 곡선을 조정해도 이 순서는 유지되어야 한다.

---

## 결정 이력

### D-001 · 노후도를 U자 곡선으로 (v1.0.0)

**가설**: 준공 연차가 늘수록 단조 감소시키면 30년 이상 단지가 부당하게 낮게 나온다.
재건축 기대가 가격에 선반영되기 때문이다.

**검증**: 30년 도달 시점에 반등하는 곡선을 만들고 골든 케이스 순서를 확인.

**결과**: 채택. 42점 저점 후 반등, 상한 68점.

**주의**: 반등폭을 더 키우면 `DEVELOPMENT` 축의 정비사업 평가와 이중 계상된다.
실제 사업 진행 단계는 확실성 계수로 DEVELOPMENT 가 평가하므로,
AGE 는 "연한 도달"이라는 사실만 반영한다.

---

### D-002 · 결측을 0점이 아닌 가중치 제외로 (v1.0.0)

**가설**: 외부 API 실패를 0점으로 처리하면 API 장애가 곧 낮은 점수가 된다.
사용자는 단지가 나쁜 건지 데이터가 없는 건지 구분할 수 없다.

**검증**: 축 3개를 강제 결측시키고 총점이 0~100 범위인지, 신뢰도가 낮게 표기되는지.

**결과**: 채택. `score: null` → 가중치째 제외 → 나머지 재정규화. 신뢰도(%) 별도 표기.

---

### D-003 · 커뮤니티 시설 미입력을 0점에서 결측으로 (v1.0.1)

**가설**: 빈 배열을 "시설이 없다"로 읽어 0점을 주고 있었다. 실제로는
"사용자가 입력하지 않았다"인 경우가 대부분이다.

**검증**: 빈 배열 + 관리비만 있는 입력에서 관리비만으로 평가되는지 확인.

**결과**: 채택. 미입력은 해당 서브스코어를 제외하고 나머지로 평가.

**교훈**: "데이터가 없다"와 "값이 나쁘다"는 다르다. 새 축을 만들 때 항상 확인할 것.

---

### D-004 · 도보 반경을 스코어링과 같은 상수로 역산 (v1.0.1)

**가설**: 지도의 "도보 10분 반경"을 별도 상수로 그리면 점수 근거와 화면이 어긋난다.

**검증**: `walkMinutes(metersForWalkMinutes(m)) === m` 을 여러 값에서 테스트로 고정.

**결과**: 채택. 표시용 상수를 따로 두지 않는다.

---

### D-005 · 계산 불능(NaN·Infinity)은 만점이 아니라 결측 (v1.0.2)

**문제**: `piecewise` 가 비유한 입력을 첫 구간 점수로 대체하고 있었다. 축 곡선 대부분이
내림차순(작을수록 좋음)이라 첫 점수가 100점이다. 즉 **통근시간·거리·비율을 산출하지 못하면
그 축이 만점을 받았다.** 순위 앱에서 나올 수 있는 가장 나쁜 실패 방식이다 —
데이터가 없는 단지가 1위로 올라오고, 화면에는 아무 경고도 뜨지 않는다.

**재현**: 좌표가 `Infinity` 면 `haversineM` 이 NaN → 모의 경로의 `totalMinutes` 가 NaN →
`piecewise(NaN, COMMUTE_CURVE)` = 100. 서버 액션의 `lat: z.number()` 는 Infinity 를 통과시킨다
(Zod 는 `.finite()` 를 붙여야 막는다).

**결정**:

1. `piecewise` 는 비유한 입력에 `NaN` 을 반환한다 — 조용히 대체하지 않는다.
2. `ok()` 가 비유한 점수를 받으면 `missing()` 으로 강등한다. 결측은 가중치째 빠지고
   신뢰도가 내려가므로, 사용자가 "이 축은 계산되지 않았다"를 화면에서 본다.
3. `blend()` · `importanceWeightedAverage()` 는 NaN 서브스코어를 제외한다.
   서브 지표 하나가 축 전체를 못 쓰게 만들 이유가 없다.
4. 집계(`computeScore`·`recomputeWithWeights`)도 유한성을 다시 확인한다.
   저장된 과거 결과를 재집계할 때의 방어선이다.
5. 좌표·가중치 입력에 범위를 건다 (`z.number().finite().min().max()`).

**원칙**: 산출 실패는 **결측으로 드러내고**, 절대 임의의 점수로 메우지 않는다.
메우는 순간 신뢰도 표기가 거짓말이 된다.

**검증**: `tests/unit/scoring/aggregate.test.ts` 의 "계산 불능 값의 결측 강등" —
NaN·Infinity 통근시간이 결측이 되고, 신뢰도가 1 미만으로 내려가며,
손상된 단지가 정상 단지보다 높은 점수를 받지 않는지 고정.

## 검증 방법

새 축이나 곡선을 바꿀 때 아래를 모두 통과시킨다.

```bash
npm test    # 경계값 · 단조성 · 결측 내성 · 골든 케이스
```

1. **경계값** — 임계 직전/직후/초과에서 의도한 값이 나오는가
2. **단조성** — 좋아질수록 점수가 오르는가 (U자 곡선은 구간별로 확인)
3. **결측 내성** — 해당 축을 결측시켜도 총점이 0~100이고 신뢰도가 내려가는가
4. **골든 케이스** — 우수 > 중간 > 열위 순서가 유지되는가
5. **버전** — `ALGORITHM_VERSION` 을 올렸는가 (안 올리면 캐시가 낡은 점수를 반환)
