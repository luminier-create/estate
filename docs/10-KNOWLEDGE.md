# 10. 지식 베이스 (누적 문서)

외부 API 정책, 도메인 지식, 비용 구조처럼 **시간이 지나면 변하는 사실**을 모은다.
확정된 스펙은 `03-DATA-SOURCES.md`, 여기는 그 스펙이 왜 그런지와 변화 추적.

## 기재 규칙

- 모든 항목에 **확신도 라벨**, **출처 링크**, **확인일** 을 붙인다
- 라벨: `[확인됨]` 공식 문서 확인 / `[검증필요]` 2차 출처만 / `[추정]` 계산·추론
- 확인일이 90일을 넘긴 `[확인됨]` 항목은 `[검증필요]` 로 강등한다
- 사실이 바뀌면 이전 값을 지우지 말고 **변경 이력**에 남긴다 — 왜 바꿨는지가 중요하다

### 1.5 공동주택관리정보시스템(K-apt) — data.go.kr Open API (로드맵 4.4 사전조사)

`[미확인]` (원문 접근 차단) 확인일 2026-09-09
출처: WebSearch 스니펫 다수(개별 URL은 아래 표기) + [luritas/open-data-api GitHub 위키](https://github.com/luritas/open-data-api/wiki/%EA%B3%B5%EB%8F%99%EC%A3%BC%ED%83%9D-%EA%B8%B0%EB%B3%B8%EC%A0%95%EB%B3%B4) (비공식 미러)

**환경 제약부터 밝힌다.** `curl` 로 직접 확인한 결과 `www.data.go.kr` ·
`apis.data.go.kr` · `dapi.kakao.com` · `api.odsay.com` 모두
`CONNECT tunnel failed, response 403` 이다 `[확인됨]` (2026-09-09).
문서 사이트뿐 아니라 **API 호스트 자체가 막혀 있어** 이 환경에서는 실호출 검증도
불가능하다. 이번 조사에서 `data.go.kr`, `k-apt.go.kr`,
`myapt.molit.go.kr`, `reb.or.kr`, `data.seoul.go.kr`, `data.gg.go.kr`,
`gimi9.com`, `velog.io`, `steemit.com`, `happycgi.com`,
`choonghyunryu.github.io`, `www.scribd.com` 등 관련 1차·2차 출처가 전부 이 작업
환경의 egress 프록시에 `EGRESS_BLOCKED`로 막혀 WebFetch로 원문을 열람하지
못했다(카카오 로컬 API 때와 같은 제약, §1.1 참고). 아래는 WebSearch 결과에
노출된 구글 색인 텍스트와, 유일하게 열람 가능했던 비공식 GitHub 위키 미러에서
얻은 **간접** 정보다. Swagger 명세서 원문을 직접 열어본 것이 아니므로 필드명·
파라미터명은 실제 개발계정 키를 발급받아 콘솔에서 재확인하기 전에는 코드에
반영하지 말 것.

**오퍼레이션 존재는 (간접적으로) 확인된다.** data.go.kr에 국토교통부 명의로 아래
오퍼레이션이 등록돼 있는 것이 검색 결과에 나타난다. URL 은 검색 결과에 노출된
그대로이며 직접 열람하지 못했다 — 전부 `[검증필요]`:

| 서비스명 | data.go.kr URL |
|---|---|
| 공동주택 기본 정보제공 서비스 | https://www.data.go.kr/data/15058453/openapi.do |
| 공동주택 단지 목록제공 서비스 | https://www.data.go.kr/data/15057332/openapi.do |
| 공동주택관리비(개별사용료)정보제공서비스 | https://www.data.go.kr/data/15059469/openapi.do |
| 공동주택관리비(장기수선충당금)정보서비스 | https://www.data.go.kr/data/15059160/openapi.do |
| 공동주택관리비(공용관리비)정보제공서비스 | 존재만 검색 스니펫으로 확인, 정확한 문서 ID 를 못 찾음 `[미확인]` |
| 공동주택 단지 관리비 정보 (파일데이터, 전국 단지·월별 집계) | https://www.data.go.kr/data/3039714/fileData.do |
| 공동주택 관리비 공개 의무단지 정보 (파일데이터) | https://www.data.go.kr/data/15098979/fileData.do |

관리비가 **공용관리비 / 개별사용료 / 장기수선충당금 3개의 별도 오퍼레이션**으로
나뉘어 있다는 점은 GitHub 위키 미러의 목차와 검색 스니펫이 일관되게 가리킨다
(`[검증필요]`). `docs/03-DATA-SOURCES.md` §6 이 이미 "㎡당 **공용**관리비"를
목표 필드로 적어뒀는데, 그렇다면 세 오퍼레이션 중 공용관리비 쪽이 우리가 쓸
값일 가능성이 높다 — 다만 정확한 응답 필드명(관리비부과면적, ㎡당 환산 여부
등)은 `[미확인]`이다.

**조회 키.** GitHub 위키 미러로 확인한 공동주택 기본 정보제공 서비스
(`AptBasisInfoService`, 엔드포인트 `http://apis.data.go.kr/1611000/AptBasisInfoService/getAphusBassInfo`,
`[검증필요]`)는 요청 파라미터로 **`kaptCode`(단지코드)** 를 요구하고 응답에
관리비 필드는 없다. 관리비 3개 오퍼레이션도 같은 계열(`kaptCode` + 조회 연월)로
설계됐을 가능성이 높지만 직접 확인하지 못했다 `[미확인]`.

우리가 분석 시점에 가진 것은 좌표·주소·법정동코드(5자리, `lawdCd`)·단지명뿐이고
`kaptCode`는 없다. 검색 스니펫 하나(원문 접근 불가한 블로그 글의 요약)에 따르면
"공동주택 단지 목록제공 서비스"가 법정동코드를 입력받아 단지코드·단지명 목록을
반환한다고 하는데, 이는 2차 출처의 요약을 다시 요약한 것이라 신뢰도가 낮다
`[미확인]`. 설령 사실이어도 "법정동코드로 받은 목록에서 우리 단지명과 문자열이
일치하는 항목을 고른다"는 매칭 로직이 별도로 필요하고, 단지명 표기 차이(예:
"OO아파트" vs "OO아파트1단지" vs "OO아파트(2차)")로 오매칭 위험이 있다.

**지역(시·군·구) 평균을 직접 주는 오퍼레이션은 발견하지 못했다.** `[미확인]`.
통계청·국토부 쪽에 시군구 단위 관리비 평균 통계가 따로 공개돼 있는지도 검색으로
찾지 못했다 — 국가지표체계에는 의무관리단지 "세대수" 현황만 있고 관리비 평균은
안 보였다(원문 미열람이라 이 역시 `[미확인]`). 즉 지역 평균이 필요하면 **해당
법정동·시군구의 단지를 모두 열거해 개별 조회한 뒤 우리가 직접 평균을 계산**해야
할 가능성이 높다. 서울 자치구 하나에도 의무관리대상(300세대 이상) 단지가 수백
개 있을 수 있어, 분석 1회(시군구 1곳 평균 산출)당 필요한 호출 건수가 지금
쓰고 있는 카카오 POI(9종)·ODsay 경로(5~6건)와는 **자릿수 자체가 다를 수 있다**
`[추정]` — 캐시 없이는 쿼터 설계가 불가능한 수준일 가능성이 있다.

**대상 범위의 구조적 한계.** 관리비 공개 의무는 **300세대 이상 공동주택**에
한정된다는 서술이 검색 결과에서 일관되게 나온다 `[검증필요]`. 사실이면 소형
단지는 애초에 K-apt 데이터가 없어 결측(`null`) 처리가 불가피하다 — CLAUDE.md의
"결측은 0점이 아니라 제외" 원칙과는 부합하지만, AMENITY 축의 관리비 서브스코어가
지금(전면 `null`)보다는 나아지되 완전히 채워지지는 않는다는 뜻이다.

**무료 티어·승인 절차는 특정하지 못했다.** `[미확인]`. 공공데이터포털 일반
정책상 "자동승인"과 "심의승인"(통상 2~3영업일) 두 갈래가 있고 개발계정은 통상
일 최대 10만 건이라는 서술을 검색에서 확인했으나, 이것이 K-apt 계열 오퍼레이션
개개에 그대로 적용되는지는 확인하지 못했다 — 국토부 실거래가(§1.3)처럼 서비스마다
승인 방식·한도가 다르게 걸리는 사례가 흔하다. 개별 신청 화면을 열기 전에는
확정할 수 없다.

추가로 "250930 공공데이터포털 오픈API 대체서비스 안내(125종)"라는 공지 문서가
검색에 노출됐다(Scribd 미러, 원문 접근 불가) — 공공데이터포털이 일부 오픈API를
정기적으로 폐지·대체 공지하는 것으로 보이는데, 이 목록에 공동주택 관리비 계열이
포함되는지는 확인하지 못했다 `[미확인]`. 실제 신청 전에 반드시 재확인이 필요하다.

**대안 — 지자체 오픈데이터.** 서울 열린데이터광장에 "서울시 공동주택 관리비
정보"(OA-15822), 경기데이터드림에 "경기도 공동주택 관련정보"가 별도로 존재하는
것으로 검색된다 `[미확인]`(둘 다 egress 차단으로 원문 미확인). 존재한다면 서울·
경기 한정으로는 지자체가 이미 집계한 형태를 받을 수 있을 가능성이 있으나, 전국
서비스인 HomeFit 입장에서는 지역별로 출처·필드가 갈리는 유지보수 부담이 생긴다.
전국 단위 대안으로는 "공동주택 단지 관리비 정보"(파일데이터, 3039714)가 있다 —
이건 실시간 API가 아니라 **주기적으로 갱신되는 다운로드 파일**이라, 쓰려면
배치로 내려받아 우리 쪽에서 미리 집계해두는 파이프라인이 필요하다(분석 요청마다
호출하는 구조가 아니게 되므로 쿼터 문제는 피하지만, 신선도는 파일 갱신 주기에
묶인다).

**우리 앱에 대한 함의**: 지금 당장 4.4를 구현하기에는 최소 세 가지가 막혀 있다.
(1) 관리비 오퍼레이션의 실제 요청·응답 스키마를 원문으로 확인하지 못해 어떤
필드가 "㎡당 월 관리비"(또는 §6이 말하는 "㎡당 공용관리비")에 대응하는지 모른다,
(2) 단지명→`kaptCode` 매칭 로직의 신뢰도를 검증할 방법이 없다, (3) 지역 평균을
직접 주는 오퍼레이션이 없어 보여 시군구 단위 집계 시 호출 건수가 쿼터 설계를
좌우하는데 그 규모조차 추정 불가하다. 개발계정 키를 실제로 발급받아 콘솔에서
Swagger 문서를 여는 것이 다음 조사의 선결 조건이며, 이 작업 환경에서는
data.go.kr 접근 자체가 막혀 있어 더 진행할 수 없었다.

분석 1회당 외부 호출: 카카오 POI 9종 + 지오코딩 1, ODsay 경로 5~6 + 정류장 1,
국토부 24개월. 국토부는 법정동 단위 캐시라 같은 지역 단지끼리 공유된다.

**결론**: Vercel + Firebase Spark 조합이면 6개월간 0원. 병목은 ODsay 하나.
