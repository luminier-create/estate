# 스코어링 축 변경 절차

점수는 사용자가 수억 원짜리 결정에 참고하는 값이다. 곡선 하나를 바꾸면
모든 단지의 순위가 움직인다. 아래 순서를 건너뛰지 않는다.

## 0. 먼저 읽는다

- `docs/01-ALGORITHM.md` — 현행 스펙
- `docs/11-ALGORITHM-LAB.md` — **이미 기각된 아이디어인지 확인**. 기각 목록에 있으면
  그 근거를 반박할 수 있을 때만 진행한다

## 1. 설계

- 구간 선형보간(`piecewise`)으로 표현한다. 임계값이 사용자 직관과 맞아야 하고,
  "왜 이 값인가"를 설명할 수 있어야 한다
- **결측 처리를 먼저 정한다.** 데이터가 없을 때 0점이 아니라 `score: null` 이다.
  "값이 나쁘다"와 "데이터가 없다"는 다르다
- 다른 축과 이중 계상되지 않는지 확인한다 (AGE 반등 ↔ DEVELOPMENT 정비사업이 그 예)
- 가중치를 바꾸면 프리셋 4종의 합이 각각 100인지 확인한다

## 2. 구현

- `src/lib/scoring/axes/<축>.ts` — 순수 함수. 외부 의존을 넣지 않는다
- 반환에 `reason`(한 줄 근거)과 `details`(항목별 설명)를 반드시 채운다.
  사용자가 점수의 근거를 볼 수 있어야 한다
- `sources` 에 데이터 출처를 남긴다

## 3. 테스트 (전부 필수)

```bash
npm test
```

- **경계값** — 임계 직전 / 직후 / 범위 초과
- **단조성** — 좋아질수록 점수가 오르는가 (U자 곡선은 구간별로)
- **결측 내성** — 이 축을 결측시켜도 총점이 0~100이고 신뢰도가 내려가는가
- **골든 케이스** — 우수 > 중간 > 열위 순서가 유지되는가. **깨지면 곡선이 잘못된 것이다**

## 4. 버전을 올린다

`src/lib/scoring/types.ts` 의 `ALGORITHM_VERSION`.
**올리지 않으면 기존 분석 캐시가 낡은 점수를 계속 반환한다.**

## 5. 문서에 남긴다

- `docs/01-ALGORITHM.md` — 곡선·가중치 표 갱신
- `docs/11-ALGORITHM-LAB.md` — 가설 → 검증 방법 → 결과 → 채택/기각.
  **기각한 것도 남긴다.** 다시 제안될 때 근거가 된다
- 골든 케이스 점수가 바뀌었으면 이전 값과 새 값을 함께 적는다

## 6. 최종 확인

```bash
npm run typecheck && npm run lint && npm test && npm run build
```

축이 화면에 노출되므로 E2E 도 한 번 돌린다.
